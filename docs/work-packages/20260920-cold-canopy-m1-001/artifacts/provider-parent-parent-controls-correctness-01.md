# COLD-CANOPY-M1 complete-parent controls — correctness review 01

**Verdict: HOLD.** The tests-first cut does not yet establish the authorized real-parent transition, independent closure, positive receiver join, or late owning rollback. Do not author the parent driver against this control cut.

**Evidence class: Static.** Independent review of canonical 760-entry source aggregate `723cd1a81e42cbd8f297b99dba63f6263187d2ac1593b8f6ad1d4ed02947a21f`. The accepted provider/admission scope was reused and not reopened. No source/configuration was edited and no test or physical command was run.

## Findings

1. **High — conservation and transaction authenticity are delegated to production self-claims.** `m1_provider_parent_controls.rs:81-88` accepts `resource_and_material_receipts_are_bound()`, `complete_parent_was_consumed_once()`, and `execution.independently_reconstructed_balance()`. All three are methods on the future driver result, so a driver can return `true` or validate its own duplicated arithmetic without exposing a wrong operand, receipt, or installation. Require raw actual per-support reservoir operands, water/root/N/material transfers, receiver receipts, and beginning/ending LSE, hydrology, soil-thermal, surface, vegetation and BGC state. Reconstruct reservoir mass/enthalpy in test code using the established independent arithmetic and tolerances in `m1_coupled_expected_red.rs:539-560`, then independently fold the typed amount-bearing receipts and compare them to exact owner deltas. Inspect concrete receipt IDs, support, units, source/destination owner, predecessor/transaction lineage, amount/enthalpy, accepted-slab membership, and consumption state. Production boolean helpers and a production-named "independent" method cannot substitute for these assertions.

2. **High — the test does not bind the 30 physical supports to all 30 admitted provider records or slab identities.** `:41-50` checks only record 0/1 ordinals, intervals, and inequality of their override arrays. It never compares any applied override to `admitted.record(n).override_binary64_bits()`, so repeating one non-first record, altering a later record, or using an unrelated changed forcing sequence could pass. `:68-73` checks only receipt count, pairwise support contiguity, and final parent end. For every `n=0..29`, assert exact record ordinal, `[60n,60(n+1))` ns support, all five applied override bit patterns, GSI value and its corresponding authenticated support receipt, accepted slab ordinal/support, beginning/ending owner-set identity, and forcing lineage against the admitted provider. Assert the first start and last end explicitly. This is the control that prevents averaging, repeating original60, skipping the rain breakpoint, or stretching one child receipt.

3. **High — the success path does not prove one consuming complete-parent installation into the real caller.** `:51-79` proves adjacent local owner-byte continuity, unchanged inactive snow, and only a top-level `parent_revision_increment()==1`; `:83-87` merely proves the caller snapshot changed. It does not show which owner bytes were installed, that every staged owner/occupancy/stratum revision followed the accepted supports, that support identities remained distinct from the persistent parent sequence, or that staging/clock/publication were cleared/advanced exactly once at the consuming seam. Replace the boolean at `:82` with concrete counters and identities: zero per-support parent publications/increments, exact accepted cursor and owner/stratum revisions across each support, one complete candidate, one commit consumption, one parent transaction increment, one publication, no remaining staged owner or live parent clock, and exact equality between all seven driver ending bytes and the post-commit real caller bytes. Bind the resulting parent/receipt identity to the ordered 30 accepted slabs.

4. **High — no concrete positive native receiver event is established inside parent zero.** The success test contains no assertion that any support produces positive canopy-liquid release and a matching actual receiver receipt. The late test's `positive_native_receiver_candidate_was_constructed()` and `receiver_capability_was_consumed()` at `:100-101` are opaque driver booleans; they do not distinguish a positive receipt from a zero-transfer candidate or a synthetic flag. Expose each support's typed zero/positive disposition and raw native candidate/receipt. Assert lawful zero-transfer supports separately, then identify the first genuinely positive support and prove positive mass/enthalpy, exact source parcel/destination/support/transaction identity, capability mint/consumption, and joined surface/hydrology/LSE/thermal receiver ending. If parent zero has no such event under the frozen forcing, the test must say so and use the separately authorized positive control rather than claim one.

5. **High — the late-rejection test can be satisfied by restoring a local clone rather than rejecting at the owning caller seam.** `:92-107` captures only the pre-parent and final caller snapshots, accepts `accepted_slab_count()>0`, and trusts three driver-reported booleans. It asserts no typed failure reason, exact injection point, accepted-slab chronology, staged caller state, candidate/receipt identity, or publication/consumption counters. A driver could do work on a disposable clone and return an unchanged caller. Require the test to reach a named late owning validation after concrete positive native receiver work and the intended authentic accepted-slab prefix, then invoke the real caller-owned candidate/commit boundary. Inspect the rejected positive candidate and receipt, assert the exact typed late error, and compare caller-owned owners, clock, staged state, accepted chronology, publication/outbox, provider continuity and live capability/consumption state before and after. The capability must be consumed on rejection with no leaked publication, and a fresh legitimate path must remain possible if required by the existing authority.

## Residual risk and missing validation

The file is intentionally expected-red because the two driver APIs are absent; compilation is not the release criterion here. The corrected controls should expose raw typed data or use test-private accessors at the real boundaries, while keeping settled primitive physics in its accepted tests. They need not duplicate the numerical solver, but they must independently reconstruct balances and inspect complete owning transitions. Provider parsing, canonical payloads, source joins, seven beginning-owner bytes, and provider admission remain accepted from body03/body04 and need no parallel reimplementation.
